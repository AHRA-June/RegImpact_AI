# 검증보고서 — 라이브 수치로 조립

브리프 §18 "코어 완성의 정의"의 종착점. **손으로 쓴 정적 문서가 아니다.**

```python
from regimpact.report import collect, render
print(render(collect()))          # 파이프라인을 실제로 돌리고 그 값으로 조립
```

생성: `python examples/build_validation_report.py` → `docs/validation/VALIDATION_REPORT.md`

기본 provider 가 `replay` 라 **LLM 호출 0회**로 재현된다. 리뷰어는 API 키 없이 같은 수치를 얻는다.

## 왜 생성하는가

보고서에 손으로 적은 숫자가 하나라도 있으면, 시스템이 바뀌는 순간 그 보고서는 **조용히
거짓말이 된다.** 검증보고서에서 이건 치명적이다 — 보고서의 존재 이유가 "이 수치를 믿어도
된다"이기 때문이다.

그래서 `collect()` 이 한 번 관통 실행하고, `validation_report.py` 는 그 결과에서만 읽는다.

| 파일 | 역할 |
|---|---|
| `evidence.py` | 파이프라인 관통 실행 → `ValidationEvidence` 한 덩어리 |
| `validation_report.py` | evidence → Markdown 렌더 |

## 하드코딩 방지

`tests/test_validation_report.py` 가 렌더러 소스를 **절 단위로** 검사한다.

- **실측 절**(`_summary`·`_s7`~`_s10`·`_s13`·`_s14`) — 수치 리터럴 **금지**
- **서술 절**(`_s3`·`_s11`·`_s12`) — 과거 값 인용이 정상. §12 발견사항의
  "Exception Recall 50%였다"는 그 시점의 사실이고 지금 값으로 바뀌면 안 된다

면제 목록이 무력화되지 않도록, 서술 절에 리터럴이 **사라지면** 오히려 실패하는 테스트를 뒀다
(기록이 지워진 것이므로).

변이 테스트로 확인했다 — 엔진 상수 `LTV_REGULATED_STANDARD` 를 0.40→0.45 로 바꾸면
보고서의 룰 diff 표가 그대로 따라온다.

## 구조

금융권 모델 검증보고서의 관례를 따른다 — 검증인이 읽는 순서다.

```
종합의견 → 배경·목적 → 범위 → 방법론 → 시스템 개요
  → 데이터 적정성 → 개념적 건전성 → 구현 정확성 → 성과 검증(추출·영향)
  → 거버넌스 → 한계 → 발견사항 → 재현성·감사추적 → 결론 → 부록
```

§12 발견사항에는 **자체 발견 결함 10건**이 심각도·조치와 함께 기록돼 있다.
숨기지 않는 것이 이 절의 목적이다(브리프 §12).
