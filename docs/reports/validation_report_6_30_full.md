## 1. Executive Summary

### 1.1 배경

2026년 6월 30일, 관계기관 합동 「가계부채 점검회의」를 통해 경기도 **화성시 동탄구·용인시 기흥구·
구리시** 3개 지역이 투기과열지구 및 조정대상지역으로 신규 지정되었고, 강화된 대출규제가 **2026년
7월 1일**부터 즉시 적용되었다. 핵심 변화는 규제지역 내 주택구입목적 주택담보대출의 **LTV가
비규제 70%에서 규제 40%로 강화**된 것이다. 이 변화는 생애최초·서민실수요·정책모기지 등 예외군,
유주택·다주택자에 대한 차등, 그리고 시행일 전일(6월 30일)까지의 접수·계약에 대한 **경과규정**을
동반한다.

이러한 규제 변경을 금융회사가 여신정책·전산 Rule·고객 영향·테스트케이스로 정확히 변환하는 작업을,
본 시스템은 **LLM 기반 초안화 + 결정론 검증**의 이중 구조로 수행한다. 본 보고서는 그 산출과
검증 과정을 평가한다.

### 1.2 검증 결론

본 검증은 **종합 PASS**로 결론한다. 근거는 다음과 같다.

- **AI 추출의 무결성(Dimension ①):** 추출된 10개 변경 항목의 인용이 **전부 원문에 verbatim으로
  존재**(Citation Correctness 100%)하며, 근거 없는 주장(Unsupported 0%)과 원문에 없는 수치 주장
  (Source Contradiction 0%)이 없다. 즉, 이 단계에서 **환각이 관측되지 않았다.**
- **완전성(Dimension ②):** 골드 기준 필수 변경을 전부 포착(Change Completeness 100%)했고,
  고위험 예외군(생애최초·서민실수요)과 경과규정을 모두 포착(Exception Recall 100%, Grandfathering
  Recall 100%)했다. 단, 이 100%는 **1차 추출의 50% 누락을 Assurance가 포착한 뒤 보완한 결과**이며,
  이 피드백 루프 자체가 본 시스템의 핵심 가치를 실증한다(§9).
- **시점 정합성(Dimension ③):** 시행일(2026-07-01)과 대상 지역을 정확히 추출했고, 효력일 경계에서
  룰엔진이 시점정합적으로 규제 전/후 버전을 반환함을 독립 오라클로 검증(Policy-version Consistency 100%).
- **룰 회귀(Dimension ④):** 룰엔진이 확정 명세와 **3,200건의 조합 입력공간 전량에서 일치**
  (Rule-regression Pass Rate 100%)하며, 경계·충돌 케이스도 전부 통과. 의도적 버그 주입(mutation)
  시 회귀가 이를 실패로 포착함을 확인하여 검증셋의 방어력을 입증했다.

종합 판정 규칙은 **고위험(★) 지표가 하나라도 FAIL이면 전체 FAIL**인 보수적(Strict) 정책을 채택했다.
현 시나리오에서는 12개 지표 전부 PASS이므로 종합 PASS다.

### 1.3 핵심 관찰

가장 중요한 관찰은 **"완벽한 점수"가 아니라 "실패를 포착하고 통제하는 능력"** 이다. 1차 추출은
저환각을 우선한 대가로 서민·실수요 예외를 놓쳐 Exception Recall 50%를 기록했고, 이를 Assurance
레이어가 고위험 지표 miss로 정확히 포착했다. 원문 근거로 보완한 뒤에도 인용 무결성(0% 환각)은
유지되었다. 이는 본 시스템이 지향하는 **"정확한 자동화"가 아니라 "검증 가능한 초안화 + 실패의
명시적 통제"** 라는 가치 제안이 실제로 작동함을 보여준다.

## 2. 검증 범위·목적

### 2.1 목적

본 검증의 목적은 RegChange AI가 6·30 규제 변경을 처리할 때 (a) AI 산출이 원문에 근거하는가,
(b) 필수 변경·예외·시점을 빠짐없이 포착하는가, (c) 결정론 룰엔진이 확정 명세를 정확히 구현하는가,
(d) 실패가 발생할 때 이를 포착하고 사람에게 escalate하는가를 정량적으로 평가하는 데 있다.

### 2.2 범위 (In-scope)

- 주택구입목적 주택담보대출의 **LTV 자동판정**(코어). DTI·대출한도는 참고값으로 제한.
- 6·30 단일 시나리오(메인 앵커) 1건.
- 파이프라인 8개 노드: 추출(E) → 영향 매트릭스 → 룰엔진 → 룰 제안 → Human Review → 회귀 →
  Assurance → 검증보고서.

### 2.3 범위 외 (Out-of-scope)

- 전세·신용·중도금·사업자 대출 제한: 추출·표면화는 하되 **Discovery(수동 검토)**로 분리, 자동판정 대상 아님.
- 정책대출(디딤돌·보금자리 등): Discovery로 분리.
- 실제 회사 내부문서·고객데이터(사용 금지).
- 다수 규제 시나리오에 걸친 일반화(실제 규제이벤트 1건만 확보).

## 3. 대상 시스템 개요

### 3.1 설계 원칙

시스템은 **확률론 축(LLM 추출)과 결정론 축(룰엔진)을 분리**하고, 결정론 룰엔진을 확률론 산출의
검증 기준점(ground truth)으로 사용한다. 규칙의 값·우선순위는 사람이 확정한 명세에서 오며,
**LLM은 규칙 로직을 생성하거나 금융 의사결정을 실행하지 않는다.** LLM의 역할은 원문에서 변경을
구조화 추출하고, 사람이 검토할 초안을 만드는 데 한정된다.

### 3.2 파이프라인

```
[1] Source Snapshot(원문+hash)
 → [2] RegChange Extractor(구조화 Before/After + 인용)
 → [3] Impact Matrix(세그먼트별 시행 전/후 LTV)
 → [R] Deterministic Rule Engine(알고리즘 H)
 → [4] Rule Change Proposal(AI초안)
 → [7] Human Review(승인 envelope)
 → [5] Test Cases + Rule-Regression(독립 오라클 차등검증)
 → [6] Assurance Scorecard(4 dimension, 확정 임계값)
 → [8] Validation Report(본 문서)
```

각 노드는 구조화 스키마(데이터 계약)로 연결되며, 모든 판정은 `reason_code`·`source_policy_id`·
`citation`으로 추적 가능하다.

### 3.3 규제 사실 기준선

| 항목 | 값 | 출처 |
|---|---|---|
| 신규 규제지역 | 구리(GURI)·용인 기흥(YONGIN_GIHEUNG)·화성 동탄(HWASEONG_DONGTAN) | MOLIT/FSC 보도참고자료 |
| 시행일 | 2026-07-01 | MOLIT 보도참고자료 |
| 경과규정 컷오프 | 2026-06-30(까지, ≤) | 관계기관 FAQ |
| 규제 표준 LTV | 70% → 40% | FAQ Q1 |
| 생애최초 | 70%(좌동) | FAQ Q2 |
| 서민·실수요 | 60% | FAQ Q2 |
| 유주택(비처분 1주택+)·다주택 | 0% | MOLIT 참고1 / FAQ |

## 4. 검증 방법론

### 4.1 차등검증(Differential Testing) — 오라클 기반

룰엔진의 정확성은 **엔진 자신의 출력을 기대값으로 쓰지 않는다.** 그렇게 하면 회귀는 항상 통과하는
tautology가 되어 무의미하다. 대신 확정 명세(05_RULE_SPEC §H)에서 **독립적으로 유도한 오라클
(challenger)**을 기준으로 삼는다. 이 오라클은 `rule_engine`·`regions`·`grandfathering`을 import하지
않고 지역 시점 해석·경과규정·판정 우선순위를 별도 코드 경로로 재구현한다. 따라서 세 모듈 어느
곳의 구현 오차든 엔진↔오라클 불일치(disagreement)로 드러난다. 이는 금융권 모델검증의 정석인
"독립 재수행(independent recalculation)"에 해당한다.

### 4.2 인용 Grounding(결정론)

AI 추출의 각 변경 항목은 `citation.quote`(원문 인용)를 동반하며, 검증기는 이 인용이 해당 원문에
**공백 정규화 후 verbatim 부분문자열로 존재하는지** 결정론적으로 대조한다. 의역·재구성·창작된
인용은 unsupported로 분류된다. 나아가 주장한 LTV %값이 인용 원문에 실제로 존재하는지 확인하여
**값 날조(Source Contradiction) 프록시**를 계산한다.

### 4.3 골드 대조

사람이 확정한 골드 정답지(`regchange_gold_6_30.json`)의 필수 변경·예외 목록과 추출을 대조하여
Change Completeness·Exception Recall·Grandfathering Recall을 산출한다.

### 4.4 시점 정합성 프로브

효력일(2026-07-01) 경계에서 3개 규제지역 × 4개 시점(6-29·6-30·7-1·7-2)에 대해 무주택 프로필을
질의하고, 엔진이 반환하는 규제 전/후 버전이 독립 오라클의 시점정합 판정과 일치하는지 측정한다.

### 4.5 임계값·스코어카드

각 지표는 확정 임계값(§13.2)으로 PASS/WARN/FAIL 판정되며, 4 dimension으로 집계된다. 종합 판정은
**고위험(★) 지표 FAIL → 전체 FAIL**, 그 외 FAIL/WARN → 전체 WARN, 전부 통과 시 PASS다.

### 4.6 방어력 검증(Mutation Testing)

검증셋이 실제로 결함을 잡는지 확인하기 위해 룰엔진에 의도적 버그(예: 서민실수요 LTV 60→65%,
유주택 0→40%, 경과규정 무력화)를 주입하고 회귀가 이를 실패로 포착하는지 확인한다. 이는 "100%
통과"가 검증셋의 무력함이 아니라 실제 일치임을 담보한다.

## 5. 데이터·평가셋

### 5.1 원문 스냅샷

3건의 공식 공문을 스냅샷으로 보존(원본 + 텍스트 추출 + hash): FSC 보도참고자료, MOLIT 보도참고자료,
관계기관 FAQ. 모든 인용은 이 스냅샷에 대해 검증된다.

### 5.2 3계층 룰 평가셋

룰엔진 검증은 서로 보완하는 3개 계층으로 구성된다.

| 계층 | 규모 | 성격 | 라벨 방식 |
|---|---:|---|---|
| seed | 30 | 사람이 읽는 대표 케이스(경계·예외·충돌) | 오라클 |
| 큐레이션 포트폴리오 | 106 | 카테고리 균형, split 부여 | 오라클 |
| 조합 격자 | 3,200 | 결정론 cartesian, 넓은 입력공간 | 오라클 |

정답을 오라클이 유도하므로 **3,200건을 손으로 라벨하지 않고** 확장할 수 있다. 큐레이션 106건은
DEV 36 / LOCKED 35 / CHALLENGE 35로 분할된다.

### 5.3 DEV / LOCKED / CHALLENGE 분리와 전량 측정의 정당성

평가 누수 방지 원칙상 LLM 튜닝용 골드셋의 LOCKED/CHALLENGE는 튜닝 종료 전까지 봉인한다. 그러나
**룰엔진은 결정론적이며 성능 튜닝 루프가 없으므로**, LOCKED/CHALLENGE를 측정해도 누수(과적합)가
발생할 수 없다. 따라서 룰 평가셋은 split을 라벨로 표기하되 전량 측정한다. 이는 계획 문서(04_PLAN
§0-5)의 정합성 해석과 일치하며, LLM 추출용 골드셋의 봉인 원칙과는 구분된다.

### 5.4 LLM 추출 골드셋의 규모 한계

추출(E) 평가의 골드셋은 **실제 규제문서 1건(6·30)** 에 기반한다. 통계적 확장을 위해 가짜 규제문서를
생성하는 것은 "실제 감독규정 vs 모의 문서"의 경계를 흐리고 프로젝트 원칙(실제 회사 문서·데이터
미사용, 규제 사실 인용 무결성)을 위반하므로 배제한다. 추출 지표는 n=1 문서셋 기준의 관측이며,
추가 실제 규제이벤트 확보 시 확대한다.

## 6. 발견사항 — Assurance Dimension별

### 6.1 Dimension ① Source Grounding & Citation — ✅ PASS

| 지표 | 값 | 임계(Strict) | 판정 |
|---|---|---|---|
| Citation Correctness | 100% (10/10) | ≥95% | ✅ |
| Unsupported Claim Rate ★ | 0% | ≤5% | ✅ |
| Source Contradiction Rate ★ | 0% | =0% | ✅ |

**분석.** 추출된 10개 변경 항목 전부의 인용이 원문에 verbatim으로 존재했다. 예컨대 LTV 변경 항목의
인용 "규제지역 내 주담대 취급시 강화된 LTV(70→40%) 적용"은 FAQ 원문 라인과 정확히 일치한다. 값
날조 검사에서도 주장된 모든 LTV %값(70%·40%·60%·0% 등)이 인용 원문에 존재하여 Source Contradiction
0%를 기록했다. **이 단계에서 환각은 관측되지 않았다.** 이는 프롬프트가 "원문에 있는 것만, 인용은
verbatim, 추론·창작 금지"를 강제하고, 검증기가 이를 결정론적으로 확인한 결과다.

**해석.** 저환각을 이 정도로 강하게 달성한 것은 완전성과의 트레이드오프를 동반한다(§6.2·§9 참조).
즉 이 dimension의 완벽한 점수는 "보수적으로 인용 가능한 것만 추출"한 결과이며, 그 대가는 완전성
측면에서 나타났다가 피드백 루프로 보완되었다.

### 6.2 Dimension ② Change & Exception Completeness — ✅ PASS

| 지표 | 값 | 임계(Strict) | 판정 |
|---|---|---|---|
| Change Completeness ★ | 100% (4/4) | ≥90% | ✅ |
| Exception Recall ★ | 100% (2/2) | ≥95% | ✅ |
| Grandfathering Recall ★ | 100% | ≥95% | ✅ |

**분석.** 골드 필수 변경 4종(LTV 70→40, 시행일, 경과규정, 규제지역 지정)을 전부 포착했고, 예외군
2종(생애최초·서민실수요)과 경과규정을 모두 포착했다. Grandfathering Recall을 Change Completeness와
분리하여 고위험 지표로 독립 노출한 이유는, 경과규정 오판이 종전/신규 규정을 뒤바꿔 대출 가부를
좌우하는 고위험 실패이기 때문이다.

**중요 단서.** Exception Recall 100%는 **1차 추출에서 50%(서민·실수요 누락)를 기록한 뒤 보완한
결과**다. 이 과정의 전모는 §9에서 상술한다. 요지는, 완전성 지표의 최종 100%가 "처음부터 완벽"이
아니라 "Assurance가 누락을 포착하고 원문 근거로 보완한" 통제 결과라는 점이다.

### 6.3 Dimension ③ Temporal / Policy-Version Consistency — ✅ PASS

| 지표 | 값 | 임계(Strict) | 판정 |
|---|---|---|---|
| Effective-date Accuracy ★ | 100% | =100% | ✅ |
| Region Completeness ★ | 100% | =100% | ✅ |
| Policy-version Consistency ★ | 100% (12/12) | =100% | ✅ |

**분석.** 시행일(2026-07-01)과 대상 지역 3곳을 정확히 추출했다. Policy-version Consistency는
효력일 경계 3지역 × 4시점(2026-06-29·06-30·07-01·07-02) = 12개 질의에 대해 엔진이 규제 전(비규제
70%)/후(규제 40%) 버전을 시점정합적으로 반환하는지를 독립 오라클로 검증한 것으로, 12/12 일치했다.
특히 6월 30일(비규제)과 7월 1일(규제)의 경계가 정확히 뒤집힌다.

**해석.** 시점 축이 이 도메인의 급소다. 하루 차이로 규제 전/후가 갈리고, 경과규정은 6월 30일까지의
접수·계약을 종전규정으로 보호한다. 본 시스템은 지역 규제상태를 시점 버전 데이터로 관리하여 이
경계를 결정론적으로 처리한다.

### 6.4 Dimension ④ Rule Regression & Conflict — ✅ PASS

| 지표 | 값 | 임계(Strict) | 판정 |
|---|---|---|---|
| Rule-regression Pass Rate ★ | 100% (3,200/3,200) | =100% | ✅ |
| Boundary-case Pass Rate | 100% (19/19, 큐레이션) | =100% | ✅ |
| Conflict-case Pass Rate ★ | 100% (10/10, 큐레이션) | =100% | ✅ |

**분석.** 3,200건 조합 격자 전량에서 엔진과 독립 오라클이 일치했다. 경계 케이스(효력일 ±1일,
경과규정 컷오프 ±1일, house_count 0/1/2/3)와 충돌 케이스(예외 동시 충족, 경과규정+유주택, 다주택+
예외 등)도 전부 통과했다. 상세는 §7.

## 7. 룰엔진 검증 심층

### 7.1 알고리즘 H와 우선순위

룰엔진은 short-circuit 우선순위 P0~P7로 판정한다: 스코프(P0) → 정책대출=Discovery(P0b) →
경과규정(P1) → 지역상태(P2) → 다주택(P3) → 유주택 비처분(P4) → 생애최초(P5) → 서민실수요(P6) →
일반(P7). 이 우선순위는 충돌 상황의 판정을 결정하며(예: 다주택+생애최초는 P3이 우선하여 0%),
오라클도 동일 우선순위를 독립 재구현한다.

### 7.2 커버리지

3,200건 격자는 다음 판정 다양성을 커버한다: **판정 상태 4종 전부**(DECIDED·OUT_OF_SCOPE·DISCOVERY·
NEEDS_HUMAN_REVIEW), **rule_id 6종**, **reason_code 11종**. 즉 명세가 정의한 모든 판정 경로가
최소 한 번 이상 검증되었다. 큐레이션 106건은 카테고리 균형(SCOPE 18·BASELINE 25·EXCEPTION 21·
BOUNDARY 19·GRANDFATHERING 13·CONFLICT 10)을 제공하여 격자의 temporal 편중을 보완한다.

### 7.3 방어력(Mutation)

의도적 버그 주입 시 회귀가 실패를 포착함을 확인했다: (a) 규제 표준 LTV 40→50%로 변조 시 무주택
관련 케이스 실패, (b) 서민실수요 60→65% 변조 시 EXCEPTION 카테고리 실패, (c) 유주택 0→40% 변조
시 실패, (d) 경과규정을 항상 미해당으로 변조 시 GRANDFATHERING 카테고리 실패. 이는 검증셋이
"이빨을 가지고 있음"을 입증한다.

### 7.4 정직한 escalation

명세에 값이 정의되지 않은 경우(예: 비규제 수도권 유주택 기준선)에는 임의값을 반환하지 않고
`NEEDS_HUMAN_REVIEW`로 escalate한다. 이는 오판보다 사람 검토를 우선하는 안전 설계이며, 영향
매트릭스에도 그대로 노출된다(§8).

## 8. 영향 매트릭스·룰 변경 제안 검토

### 8.1 시행 전/후 영향 (구리 기준)

| 세그먼트 | 시행 전 | 시행 후 | Δ | 방향 |
|---|---|---|---|---|
| 무주택 일반 | 70% | 40% | -30pp | 강화 |
| 생애최초 | 70% | 70% | 0pp | 동일(예외 보호) |
| 서민·실수요 | 70% | 60% | -10pp | 강화 |
| 처분조건부 1주택 | 70% | 40% | -30pp | 강화 |
| 비처분 1주택 | (기준값 부재) | 0% | — | 검토 필요 |
| 다주택 | (기준값 부재) | 0% | — | 검토 필요 |

**분석.** 영향은 룰엔진을 시행 전(2026-06-30)·후(2026-07-02) 두 시점으로 차등 실행한 결과다.
무주택 일반이 -30pp로 가장 큰 타격을 받고, 생애최초는 예외로 보호되어 변화가 없다. 주목할 점은
**유주택·다주택 세그먼트가 "검토 필요"로 표시**된 것이다. 이는 명세가 비규제 수도권 유주택의
기준선 LTV를 정의하지 않아 시행 전 판정이 escalation되기 때문으로, 시스템이 없는 값을 지어내지
않고 정직하게 공백을 노출한 결과다. 이 공백은 규제 사실 검수(OPEN_QUESTIONS Q6) 시 해소 가능하다.

### 8.2 룰 변경 제안 — AI초안 → 사람 확정

룰 변경 제안은 영향 매트릭스에서 유도되며(하드코딩 없음), 초기 상태는 **PENDING_REVIEW(AI초안)**
이다. 제안 각 행은 세그먼트·rule_id·전후 LTV·reason_code·검토 필요 여부를 담는다. 사람 검토
(`record_decision`)를 통해 APPROVED/REJECTED/CHANGES_REQUESTED로 확정되며, 제안 본문은 불변으로
유지되어 감사 추적에 유리하다. 유주택·다주택 2개 행은 `needs_review=True`로 표시되어 자동 확정에서
제외된다.

## 9. 고위험 실패 분석 및 피드백 루프

### 9.1 관측된 실패: 서민·실수요 예외 누락

1차 추출은 인용 무결성을 우선한 결과, FSC 보도참고자료의 "생애최초 주택구입, 정책모기지 등은
완화된 LTV 규제비율(60~70%) 적용" 문장만 인용하고 **서민·실수요자 예외를 별도 항목으로 표면화하지
않았다.** 이로 인해 Exception Recall이 **50%(1/2)** 로 측정되었다. 서민·실수요 예외는 실제로는
관계기관 FAQ Q2에 존재하는 규제 사실이다.

### 9.2 Assurance의 포착

Exception Recall은 고위험(★) 지표로, 임계값 미달(50% < 95%) 시 해당 지표 FAIL → 종합 FAIL이다.
즉 **Assurance 레이어가 이 누락을 자동으로 포착하여 escalate**했다. 이는 프롬프트 원칙("완전성보다
저환각 우선")이 만든 구조적 트레이드오프를 검증 레이어가 정확히 드러낸 사례다.

### 9.3 보완과 재측정

포착된 누락을 FAQ Q2 원문 근거(verbatim: "규제지역에서도 금융권 생애최초 주담대*, 금융권 서민·
실수요자 주담대*, 정책모기지 등에 대해서는 완화된 LTV가 적용됨")로 보완하여 서민·실수요 예외
항목을 추가했다. 재측정 결과 **Exception Recall이 100%로 상승**했고, 새 인용 역시 verbatim이므로
**인용 무결성(Citation 100%·Contradiction 0%)은 유지**되었다. 즉 완전성을 올리면서 환각을 늘리지
않았다.

### 9.4 의미

이 사건은 본 시스템의 핵심 가치를 실증한다. **측정 → 결함 포착 → 근거 기반 보완 → 재측정**의
검증 루프가 실제로 한 바퀴 돌았고, 각 단계가 산출물과 테스트로 고정되었다(추출 산출물의 `_meta.
iteration`, 회귀 고정 테스트). Model Risk 관점에서 중요한 것은 "처음부터 완벽했는가"가 아니라
"실패를 포착하고 통제 가능한 경로로 되돌릴 수 있는가"이며, 본 사례가 그 능력을 보여준다.

## 10. 한계·가정

본 검증의 한계를 명시한다(과대약속 방지).

1. **표본 규모.** 실제 규제문서 1건(6·30) 기준이다. 추출 지표(Dimension ①②③의 골드 대조 부분)는
   n=1 문서셋의 관측이며 통계적 검정력을 주장하지 않는다. 목표는 검정력이 아니라 **실패모드 층화
   커버리지 + 넓은 입력공간 명세 일치**다.
2. **오라클의 성격.** 룰 회귀의 기준은 확정 명세에서 독립 유도한 challenger이지 제3자 벤치마크가
   아니다. 100% 통과는 "엔진 = 명세" 일치를 뜻하며, **명세 자체의 정합성**은 별도 검수 대상이다
   (일부는 Q6·Q8로 표면화됨).
3. **Source Contradiction의 근사성.** 값 존재 여부(%-토큰) 기반 프록시이며 의미론적 모순(NLI)을
   완전히 탐지하지는 않는다. 향후 심화 대상이다.
4. **추출의 provenance.** 본 검증에서 LLM 추출 단계는 Claude Code 세션에서 프롬프트 규칙에 따라
   수동 grounded 추출로 수행되었다(자동 무인 API 실행이 아님). Assurance 채점은 전부 결정론 오프라인
   코드로 산출되어 이 부분의 수치는 재현 가능하다. 자동 claude-opus-5 API 무인 실행 1회는 API 키
   확보 후 후속으로 남긴다.
5. **명세 공백.** 비규제 수도권 유주택 기준선 등 명세 미정의 영역은 escalation으로 처리되며, 이는
   오판을 피한 정직한 처리이지만 해당 세그먼트의 정량 임팩트는 산출되지 않는다.
6. **범위.** LTV 코어에 한정되며 DTI·한도·전세·신용 등은 참고/Discovery다.

## 11. 거버넌스·Human Review·감사추적

- **Human Review(Approval envelope):** 룰 변경 제안은 초안으로 생성되어 사람 확정을 거친다. 검토
  결과(status·검토자·노트·시점)가 기록되고 제안 본문은 불변이다.
- **Escalation:** 명세 공백·모순 입력은 자동 판정 대신 `NEEDS_HUMAN_REVIEW`로 escalate한다.
- **추적성(INFRA):** 모든 판정은 `reason_code`·`applicable_rule_id`·`source_policy_id`를 동반하고,
  추출은 `citation`을, 소스는 hash를 보존한다. 결정론 재현으로 동일 입력→동일 출력이 보장된다.
- **감사 로그(계획):** 정식 append-only audit trail은 미구현이며, 현재는 approval 기록·소스 hash·
  결정론 재현이 부분적으로 이를 대체한다.

## 12. 결론·권고

### 12.1 결론

6·30 규제 변경 시나리오에 대해 RegChange AI는 **원문 추출부터 검증보고서까지 E2E로 관통**하며,
Assurance 4 dimension 12개 지표를 확정 임계값(Strict) 기준으로 **전부 충족(종합 PASS)**한다. 특히
AI 산출의 환각이 관측되지 않았고, 룰엔진은 3,200건 입력공간에서 확정 명세와 일치하며, 검증셋의
방어력(mutation)이 확인되었다. 무엇보다 완전성 누락을 Assurance가 포착하고 근거 기반으로 보완한
피드백 루프가 실증되어, 시스템의 통제 능력을 입증한다.

### 12.2 권고

1. **자동 LLM 실행 재현:** API 키 확보 시 자동 추출 1회를 실행하여 수동 grounded 추출 수치와 비교·
   재현한다(provenance 강화).
2. **명세 공백 해소:** 비규제 수도권 유주택 기준선(Q6)과 유주택+생애최초 모순 처리(Q8)를 도메인
   검수로 확정하여 escalation 항목을 축소한다.
3. **정식 감사 로그:** append-only audit trail을 구현하여 추적성을 인프라 수준으로 완성한다.
4. **추출 골드셋 확대:** 추가 실제 규제이벤트 확보 시 추출 평가를 다문서로 확대하여 통계화한다.
5. **Assurance 심화:** Source Contradiction의 의미론적 탐지(NLI)와 escalation 계열 정량화를 후속
   dimension으로 검토한다.
