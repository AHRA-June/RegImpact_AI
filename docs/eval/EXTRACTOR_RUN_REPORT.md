### D-01 지역 어휘 불일치 — `[✅ 해결]`
- **증상:** 추출기가 `["화성시 동탄구", "용인시 기흥구", "구리시"]`(한글 표기)를 냈는데

- **본질:** 환각이 아니라 **컴포넌트 간 인터페이스 결함**. E2E 관통을 실제로 깨는 종류.

  (`regimpact.extractor.normalize_regions`)를 추가. 매핑 실패는 버리지 않고 `unmapped`로 표면화.

### D-02 열거 병합에 의한 예외 누락 — `[✅ 해결 2026-08-18]`

> **해결:** 문서별 개별 추출 + 문서 간 병합으로 **Change Completeness 79%→100%,
> Exception Recall 50%→100%.** 아래는 발견 당시 기록이며, 해결 과정은 §6에 이어진다.

- **증상:** Exception Recall 50%. 골드의 `real_demand`(서민·실수요자)를 **두 모델 모두** 놓쳤다.
- **원인:** FSC 보도자료는 "생애최초 주택구입, 정책모기지 **등**"으로 축약해 서술하고,
  FAQ(`faq_20260630.txt` L52)만 "생애최초 주담대, **서민·실수요자 주담대**, 정책모기지 등"으로
  전부 열거한다. 모델은 짧은 쪽(FSC)을 인용원으로 골라 "등"에 흡수된 항목을 잃었다.
- **시도한 조치:** 프롬프트 v2에 규칙 6("열거를 병합·축약하지 마라") + 규칙 7("문서 교차 확인,
  가장 자세한 서술 기준") 추가 → 추출 건수는 15→19로 늘었지만 **이 항목은 여전히 누락**.
- **판단:** 앵커 1건에 프롬프트를 더 맞추는 것은 과적합이자 지표 게이밍이다. 여기서 튜닝을 멈추고
  **확인된 결함으로 기록**한다. 실제 해결은 Phase 2에서 DEV 40건 전체를 상대로 진행한다.
- **왜 중요한가:** 예외 누락은 이 시스템의 **high-risk 실패 유형**이다(예외를 못 보면 규제 적용을
  과대·과소 판정). 이 프로젝트의 가치 제안("실패의 명시적 통제")이 실제로 작동한 첫 증거다.
- 후보 대책: ①문서별 개별 추출 후 union(문서 간 축약 손실 차단) ②"등/기타" 토큰 감지 시
  다른 문서에서 열거 확장 강제 ③예외 항목 전용 2차 패스.

### D-03 ~~모델 등급에 따른 인용 환각~~ → **측정 오차였음** — `[❌ 철회 2026-08-18]`
- **최초 보고:** "haiku-4-5는 Unsupported Claim Rate 25%(3/12), sonnet-5는 0% — 모델 선택이
  곧 리스크 프로파일 선택이다."
- **재검증 결과: 틀렸다.** 저장된 haiku 실행의 인용 3건을 원문과 직접 대조해 보니 **12건 전부 원문에
  존재**했다. Unsupported Claim Rate는 25%가 아니라 **0%** 다.
- **원인:** 채점기의 인용 대조가 공백을 "단일 공백으로 축약"만 하고 있었다. 그런데 PDF/HWP
  추출본은 문장은 물론 **단어 중간에서도 줄을 바꾼다**("규제\n지역 내"). 모델이 이를 자연스러운
  "규제지역 내"로 옮겨 적으면 축약 기준에서는 불일치가 된다. **모델이 인용을 지어낸 것이 아니라
  채점기가 원문 추출 아티팩트를 환각으로 오인한 것이다.**
- **조치:** 대조 정규화를 공백 **전부 제거**로 변경(`extractor/evaluate.py::_norm`).
  다른 단어를 지어낸 인용은 여전히 잡힌다 — 회귀 테스트 2건으로 양방향 고정
  (`test_grounding_tolerates_pdf_line_breaks_inside_words`, `test_grounding_still_catches_fabricated_wording`).
- **남는 실제 차이:** 인용 무결성은 두 모델이 같다. 차이는 **추출 완전성**이다 —
  sonnet-5 19건 vs haiku-4-5 12건(동일 프롬프트·원문). 코어 모델을 sonnet-5로 두는 결정은
  유지하되, 근거는 "인용 환각"이 아니라 "열거 포착 건수"로 정정한다.
- **교훈:** 지표가 나쁘게 나왔을 때 모델을 의심하기 전에 **측정기를 먼저 의심해야 한다.**
  같은 오차가 골드셋 QA 평가 첫 실행에서도 반복됐다(`GOLDSET_EVAL_REPORT.md` §2).

## 6. D-02 해결 — 문서별 추출 + 문서 간 병합 (2026-08-18)

### 6-1. 먼저 골드를 고쳤다
v1 골드는 required 4 / exception 2로 **튜닝 근거가 되기엔 너무 얇았다**. 6·30 코퍼스에서 실제로
검증 가능한 사실 19개 + 예외 4개로 확장(v2). 확장하자마자 단일 패스의 실제 성적이 드러났다:

| | Change Completeness | Exception Recall | 놓친 항목 |
|---|---:|---:|---|
| 단일 패스(sonnet-5) | **79%** | **50%** | 서민·실수요자, 유주택 0%, 최대한도 6억, 전입의무 |
| 단일 패스(haiku-4-5) | 53% | 25% | 위 + 정책모기지, 토허제 시행일, 경과규정 3종 |

v1 골드에서 "Completeness 100%"였던 것이 v2에서는 79%다. **지표가 좋았던 것이 아니라
골드가 물었던 것이 적었다.**

### 6-2. 원인은 문서 간 그림자
누락 4건 중 3건(유주택 0%·최대한도·전입의무)이 MOLIT에, 1건(서민·실수요자)이 FAQ에 있었다.
3개 문서를 한 번에 태우면 한 문서의 축약된 서술("생애최초, 정책모기지 **등**")이 다른 문서의
완전한 열거를 가린다. 프롬프트로 "축약하지 마라"고 지시해도 두 모델 모두 같은 실패를 반복했다.

### 6-3. 대책: 문서마다 따로 추출한 뒤 합친다
각 문서를 볼 때는 그 문서의 서술이 유일하므로 가려질 대상이 없다.

| | 단일 패스 | **문서별 추출 + 병합** |
|---|---:|---:|
| 추출 항목 | 19 | **75** (원시 82 → 동일 1 + 문서 간 6 병합) |
| Change Completeness | 79% | **100%** |
| Exception Recall | 50% | **100%** |
| Citation Correctness | 100% | **100%** |
| LLM 호출 | 1회 | 3회 (문서 수) |
| 소요 | ~1.5분 | ~8분 |

비용은 3배지만 무과금 경로라 지출은 여전히 0원이다. 문서별 결과를 원문 해시 키로 캐시하므로
재실행·후속 단계 실패 시 이미 끝난 문서를 다시 부르지 않는다.

### 6-4. ⚠️ 유사도 병합은 기각했다 — 지표가 통과했는데도
문서별 추출은 같은 사실을 문서 수만큼 만든다(LTV 70→40이 3건). 요약문 유사도로 합치려 했고,
**골드 대비 점수는 임계값 0.3까지 내려도 100%/100%를 유지했다.** 그런데 실제로 무엇이 합쳐지는지
열어 보니 임계값 0.6에서도 이런 병합이 일어나고 있었다:

- "생애최초 60% 유지" + "서민·실수요자 60% 유지" → **서로 다른 차주 유형**
- "서민 요건 9천만원/8억" + "생애최초 요건 7천만원/6억" → **서로 다른 임계값**
- "일반 주담대 경과규정" + "사업자 주담대 경과규정" → **서로 다른 규제**

개체만 다르고 문장 구조가 같아 텍스트 유사도로는 구분되지 않는다. **임계값 문제가 아니다.**
골드가 100%였던 이유는 골드의 사실들이 넓어서 다른 항목이 대신 맞혀 주었기 때문이다 —
**골드가 과병합을 탐지할 만큼 예민하지 않았다.** 지표만 보고 채택했다면 D-02를 병합 단계에서
되살릴 뻔했다.

**바꾼 규칙:** 같은 문서 안의 항목은 건드리지 않는다(모델이 나눴다면 나눈 이유가 있다).
합치는 것은 **서로 다른 문서가 같은 사실을 말한 경우뿐**이고, 조건 셋을 모두 만족해야 한다 —
①출처 문서가 다름 ②내용 지문(카테고리·수치·개체어) 일치 ③요약문 유사도 ≥ 0.5.
합쳐진 항목은 다른 문서의 인용을 `corroborations`로 보존하므로 근거가 오히려 강해진다.

### 6-5. 하위 영향: 매트릭스 행 16 → 30
Discovery 행이 4 → 18로 늘었다(실제로 그만큼 있었다). 이때 자동처리율이 50%→27%로 '하락'했는데,
Discovery는 정의상 수동이므로 **탐지를 잘할수록 지표가 나빠지는 구조**였다. 분모를 코어 행으로
고정해 바로잡았다 → 코어 자동처리 **67%**. (앞선 "자동판정 불가 22.4%"와 같은 종류의 분모 문제다.)

## 7. 골드 v3 — 검수 중 측정 품질 정비 (2026-08-18)

23항목 도메인 검수를 준비하며 각 entry가 **실제로 무엇을 재는지** 측정했다. 채점 키워드가
추출 결과 75건 중 몇 건에 걸리는지 세어 보니 세 종류의 문제가 나왔다.

| 문제 | 예 | 조치 |
|---|---|---|
| 이중 측정 | `EXC_FIRST_HOME`(required)과 `first_home_buyer`(exception)의 키워드가 **동일** | required에서 제거 — exception_recall이 이미 잰다 |
| 키워드 과잉 | `SCOPE_JEONSE`가 "전세대출"로 **17건**에 매칭 → 사실상 항상 통과 | "3억원 초과 APT"로 좁힘(5건) |
| 값 전이를 못 잼 | `LTV_BASELINE_70`이 "70%"만 봐서 생애최초 70%에도 걸림 | `transition` 신설 — before/after 필드를 직접 대조 |

**`transition` 채점 신설이 핵심이다.** 기존 채점은 summary·before·after를 이어붙인 문자열에서
키워드를 찾았기 때문에 "70%가 어딘가 있다"까지만 볼 수 있었다. 이 제품의 핵심 주장이
**"무엇이 무엇으로 바뀌었는가"** 인 이상, 전이는 전이로 채점해야 한다.

```json
{"id": "LTV_REGULATED_40", "transition": {"before": "70%", "after": "40%"}}
```

### 엄격해진 뒤에도 100%였다

| | required | Change Completeness | Exception Recall |
|---|---:|---:|---:|
| v2.1 (느슨) | 19 | 100% | 100% |
| **v3 (엄격)** | **16** | **100%** | **100%** |

이게 중요하다 — **기존 100%가 느슨한 키워드 덕이 아니었다는 뜻**이다. 더 어려운 시험을 통과했다.
단일 패스는 같은 v3 기준에서 88% / 50%이므로 문서별 추출의 개선폭도 그대로 유지된다.

### 부수로 잠복 버그를 찾았다
`req.get("id", req["keywords"][0])` — 파이썬은 `dict.get`의 기본값을 **먼저 평가**하므로,
키워드가 빈 entry(전이 전용)에서 `IndexError`로 채점이 죽는다. 회귀 테스트로 고정했다.

> ⚠️ **분모가 바뀌었다.** v3의 required는 16이므로 v2.1(19)의 수치와 직접 비교하지 않는다.

### ✅ 사용자 검수 완료 (2026-08-18)

20항목(필수 16 + 예외 4) 전부 **인용이 주장을 뒷받침함**을 사용자가 확인했다. 전 항목
`authored_by: human_confirmed`, 확정 지문 `098cd126`.

**이 시점부터 위 수치는 상대 비교용이 아니라 확정 근거를 가진 값이다.** 그 전까지는
"골드가 초안이므로 절대값은 검수 후 재확인"이라는 단서가 붙어 있었고, 이제 그 단서가 사라졌다.

골드를 이후에 손보면 지문이 어긋나 검증기가 재검수를 요구한다(`pytest -k confirmation`).
