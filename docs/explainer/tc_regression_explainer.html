무엇을, 왜 만들었나

이전 세션에서 "규제 대출 신청 → LTV 몇 %"를 자동 계산하는 룰엔진은 이미 만들어져 있었습니다. 이번 작업은 그 엔진을 믿을 수 있는지 검증하는 장치를 만든 것입니다. 세 부품으로 구성됩니다.

오라클 (채점기)

규제 명세를 보고 엔진과 무관하게 처음부터 다시 구현한 "정답 계산기". 엔진 코드를 한 줄도 참조하지 않습니다.

생성기 (문제 출제)

경계·예외·충돌 등 버그가 잘 나는 지점을 노려 30개 시나리오를 체계적으로 만듭니다. 정답은 오라클이 채웁니다.

회귀 하네스 (채점)

각 시나리오를 엔진과 오라클 둘 다에 넣고 답이 같은지 비교해, 카테고리별 통과율을 냅니다.

이 방식의 이름: 차등 검증 (Differential Testing) · 챌린저 모델

금융권 Model Risk / 모델검증 직무의 표준 기법입니다. "실무 모델(엔진)"을 "독립적으로 만든 도전자(오라클)"와 맞대어, 둘의 불일치를 곧 버그 신호로 삼습니다.

02 왜 오라클이 필요한가

"동어반복(tautology)" 함정

검증할 때 흔한 실수는 엔진에게 문제를 풀게 하고, 그 답을 정답지로 삼아, 다시 엔진으로 채점하는 것입니다. 당연히 항상 100% 맞지만 — 아무것도 검증하지 못합니다.

✗ 잘못된 방식
1엔진이 문제를 푼다
2그 답을 "정답지"에 적는다
3엔진으로 다시 채점한다 → 항상 100%

엔진의 버그가 정답지에도 그대로 복사되어 영원히 안 잡힘.

✓ 채택한 방식
1명세를 보고 오라클을 따로 만든다
2엔진과 오라클이 각자 문제를 푼다
3두 답을 비교한다 → 다르면 버그

두 구현이 서로의 감시자가 된다.

06 핵심

오라클은 실제로 어떻게 "독립"인가

핵심은 오라클이 엔진의 부품을 하나도 import하지 않고, 같은 계산을 처음부터 다시 짠다는 것입니다. 세 지점을 실제 코드로 나란히 비교합니다.

독립성 ① — import 자체가 다르다

엔진 rule_engine.py
# 부품을 가져다 씀
from .grandfathering import is_grandfathered, is_owner
from .regions import resolve_region_status
오라클 oracle.py
# 그 부품들을 안 가져옴 — 스키마만 공유
from ..models import (EvaluationStatus,
    LoanPurpose, MortgageApplication)
# rule_engine / regions / grandfathering → 없음
이 독립성을 기계가 강제한다

테스트 test_oracle_does_not_import_rule_engine가 오라클의 import문을 AST로 파싱해서 금지 모듈이 들어오면 실패시킵니다. "독립성"이 사람 약속이 아니라 자동 검사 규칙입니다.

독립성 ② — 지역 판정을 따로 구현

엔진 regions.py
# 버전 테이블을 순회하며 날짜 구간 매칭
for v in REGION_VERSIONS.get(code, []):
    after  = v.effective_from is None or d >= v.effective_from
    before = v.effective_to   is None or d <= v.effective_to
    if after and before:
        return v.status, v.regulated_type
오라클 oracle.py
# 테이블 없이, 사실을 직접 조건식으로
def _region_is_regulated(code, as_of):
    if code in _SIX_THIRTY_REGIONS \
       and as_of >= _REG_EFFECTIVE:
        return True
    return False

같은 규제 사실, 완전히 다른 코드. 만약 regions.py가 >=를 >로 잘못 쓰면 (효력일 당일 판정이 어긋남) 오라클은 여전히 >=로 계산하므로 BND-EFF-02에서 두 답이 갈라지고 = 버그가 잡힙니다.

독립성 ③ — 경과규정도 따로 구현

엔진
# grandfathering.py의 함수를 호출
grandfathered, reason = is_grandfathered(app)
오라클
# G1/G2/G3를 자기 안에서 다시 판정
def _is_grandfathered(app):
    if app.application_accepted_at <= _GF_CUTOFF:
        return "GRANDFATHERED_ACCEPTED_OR_CONTRACT"
    # ... G2(계약+계약금), G3(토허제) 동일하게
    return None
왜 결과는 같아야 하나?

독립적으로 짰지만 둘 다 같은 명세(§H)의 올바른 구현이라면 답은 항상 같아야 합니다. 평소엔 30개 전부 일치(100%). 한쪽에 버그가 생기면 답이 갈라져 반드시 드러납니다 — 구현 방식을 일부러 다르게 했기에 같은 오타가 양쪽에 복제될 확률이 낮습니다.

07 검증 장치를 다시 검증

Mutation Test — 이 fixture에 이빨이 있는가?

30개 다 통과했다고 검증 장치가 제대로 작동한다는 보장은 없습니다. 혹시 무조건 통과시키는 껍데기라면? 그래서 일부러 엔진에 버그를 심고, 회귀가 그 버그를 잡는지 확인했습니다.

돌연변이 1 LTV 상수 조작
△규제 표준 LTV를 40% → 50%로 몰래 변조
✓회귀 통과율이 100% 밑으로 떨어짐
✓EXC-01·BND-HC-* 케이스가 실패로 잡힘
돌연변이 2 경과규정 무력화
△경과규정 판정을 항상 "미해당"으로 변조
✓회귀 통과율 하락
✓GRANDFATHERING 카테고리가 실패로 잡힘
이게 있어야 "100% 통과"가 의미를 가진다

돌연변이를 심으면 반드시 실패한다는 걸 보였기 때문에, 평소의 100%는 "장치가 무력해서"가 아니라 "엔진이 실제로 맞아서"임을 증명할 수 있습니다.

09 덤으로 발견

명세 자체의 모순 (Open Question Q8)

케이스를 만들다가 규제 명세 문서 안에서 서로 모순되는 서술을 발견했습니다. "유주택 + 생애최초"라는 (논리상 모순인) 입력이 들어올 때:

명세 §E 주석
