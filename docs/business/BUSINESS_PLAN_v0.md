### 제품이 만들어내는 결과물 (실물 기준)

```
공식 원문(금융위/국토부 보도자료·FAQ)
 → 원문 스냅샷 + sha256 해시 저장
 → 유효 정책 버전 판정(시행일·경과규정·지역상태)

 → 구조화 Rule 변경안 (YAML, LLM은 코드를 수정하지 않음)
 → 경계·예외·충돌 테스트케이스 자동 생성
 → deterministic 룰엔진 회귀 검증 (독립 오라클과 차등 대조)
 → Assurance 지표 산출 + 사람 승인 → 감사증적(audit trail)
```

# 1. 문제인식 (Problem)

## 1.1 창업 아이템의 배경과 필요성

### (1) 문제의 본질: 병목은 "규정 읽기"가 아니라 "시간 압축"이다

정부의 부동산·가계대출 대책은 **발표와 시행 사이 간격이 극단적으로 짧다.**

**실제 사례 — 2026년 6·30 규제지역 지정 건 (본 프로젝트 메인 시나리오, 원문 스냅샷 보유)**

| 시점 | 사건 |
|---|---|
| 2026-06-29 | 국토부 주거정책심의위 의결 |
| 2026-06-30 | 발표 (화성 동탄구·용인 기흥구·구리시 규제지역 및 토지거래허가구역 신규 지정) |
| **2026-07-01** | **시행 — 발표 다음 날** |

이 하루 사이에 금융회사가 반드시 끝내야 하는 일:

1. 무엇이 바뀌었는지 파악 (LTV 70%→40%, 생애최초 70%, 서민실수요 60%, 다주택 0% 등)
2. 예외·경과규정 해석 (6.30까지 접수 완료 또는 계약 체결+계약금 납부 증빙 시 종전규정)
3. 영향 고객군 식별 (기존 신청건 중 경과규정 대상은 누구인가)
4. 여신심사 Rule 변경안 확정 → 내규 개정 상신 → 위원회 승인
5. 전산 요건서 작성 → IT 개발 요청 → 쿼리·변수 수정
6. **"에러 나는 테스트건"을 수작업으로 만들어** 오류가 없을 때까지 반복 테스트
7. 시행 전날까지 전산 반영 완료 (수기운영 회피) → 현업 공지

> **창업자 본인이 8년 7개월간 이 업무를 직접 수행한 당사자다.** 6·30 같은 건이 뜨면 시행 전날까지 야근으로 테스트케이스를 손으로 만들며 전산 반영을 마쳤다. 이 문서의 문제정의는 시장조사 리포트가 아니라 **실무 경험의 재구성**이다.

### (2) 왜 지금까지 해결되지 않았나

| 기존 대응 방식 | 한계 |
|---|---|
| 담당자 수작업 (현행 표준) | 시간 압축 구간에 인적 오류 집중. 예외·경과규정 누락이 사고로 직결 |
| 외부 컨설팅 | 발표 다음날 시행 속도를 못 따라감. 단가 높고 반복 불가 |
| 사내 챗봇/RAG 도입 | "규정을 요약해주는" 수준. **틀렸을 때 검증할 방법이 없어** 여신 Rule 변경 근거로 쓸 수 없음 |
| 범용 LLM (ChatGPT 등) | 시행일·경과규정·정책버전 충돌에 취약. 인용 없는 주장(환각)이 규제 판단에 유입되면 통제 불가. 외부 전송 이슈 |

**핵심 공백:** 금융권은 이미 LLM을 도입하고 있지만, **그 결과물을 "규제 판단에 써도 되는가"를 증명하는 레이어가 없다.** 우리는 이 공백을 제품의 본체로 삼는다.

### (3) 오류의 비용 — 왜 정확도가 아니라 "검증 가능성"인가 `[가정 — 고객 인터뷰로 검증 필요]`

규제 미반영·오적용 시 발생하는 비용:

- 소급 정정: 잘못 실행된 대출건 재심사·한도 조정·고객 재안내
- 감독당국 리스크: 검사 지적, 개선요구, 내부통제 미비 판단 가능성
- 평판 리스크: 고객 민원 및 언론 노출
- 기회비용: 담당 인력의 야근·대체업무 중단

> `[검증필요]` 위 항목별 금액 환산은 아직 근거가 없다. 멘토링 이후 **현직 실무자 5~10명 인터뷰**로 ① 규제 1건당 투입 공수(인×일) ② 최근 3년 오적용/재작업 발생 빈도 ③ 이를 줄이는 데 지불 의사가 있는 금액을 확보한다. → §5 검증 계획

## 1.2 목표시장(고객) 현황·분석

### (1) 시장 정의 — Bottom-up

| 구분 | 대상 | 산정 근거 |
|---|---|---|
| **TAM** | 국내 여신 취급 금융회사 전체 (은행·저축은행·상호금융·여신전문·보험) `[검증필요: 기관 수는 금융통계정보시스템 기준으로 확정]` | 가계여신 규제 대응 의무를 지는 모든 기관 |
| **SAM** | 그중 **주택담보대출을 자체 심사 룰로 운영**하고, 규제변경 대응을 전담 조직이 수행하는 기관 (은행·저축은행 상위권·상호금융 중앙회) | 룰엔진·전산 반영 프로세스가 존재해야 제품이 붙음 |
| **SOM (3년)** | SAM 중 **선도 도입 10~15개사** `[가정]` | 초기 레퍼런스 1~2개사 확보 후 동종업권 확산 가정 |

> `[검증필요]` 위 표의 기관 수·금액은 **아직 채우지 않았다.** 근거 없는 큰 숫자를 쓰지 않는 것이 이 제품의 브랜드(Assurance)와 일치한다. 확정 시 출처는 금융통계정보시스템·금융감독원 업무보고서 등 **1차 출처만** 사용한다.

### (2) 고객 세그먼트와 구매 결정 구조

| 세그먼트 | Pain | 예산 보유 | 초기 진입 난이도 |
|---|---|---|---|
| **개인여신정책부** (1차 사용자) | 규제 해석·룰 변경안 작성 | 중 | 낮음 — 실사용자, 효과 즉시 체감 |
| **리스크관리/모델검증** (챔피언 후보) | AI 결과 검증 근거 필요 | 중~상 | 중 — Assurance 지표가 곧 이들의 언어 |
| **준법감시/내부통제** | 감사증적·근거 추적 | 상 | 중 |
| **IT 여신개발** | 요건서 품질·테스트케이스 | 중 | 낮음 |
| **저축은행·상호금융** | 전담 인력 부족이 더 심각 | 하~중 | 높음(예산) / 낮음(니즈) |

**구매 결정 구조 `[가정]`:** 실사용자(정책부)가 필요를 느끼고, **리스크·준법 부서가 "검증 가능하다"고 승인해야** 도입된다. → 제품이 Assurance를 본체로 삼는 이유가 곧 영업 전략이다.

### (3) 경쟁 환경

| 경쟁군 | 대표 유형 | 우리의 포지션 |
|---|---|---|
| 범용 LLM/사내 챗봇 | ChatGPT, 사내 RAG | 우리는 요약이 아니라 **룰·테스트·회귀까지 전파**. 검증 지표를 산출 |
| 국내 레그테크 | 규정 검색·컴플라이언스 문서관리 | 우리는 **여신 Rule·전산 요건·테스트케이스**라는 실행 산출물까지 연결 |
| 컨설팅펌 | 규제대응 자문 | 반복 가능·즉시 실행·저비용. 컨설팅은 협업 채널로도 활용 가능 |
| 금융사 자체 개발 | 사내 AI TF | 도메인 룰 명세·평가셋·회귀 하네스를 자체 구축하는 비용이 큼. **우리는 그 검증 자산 자체를 판매** |
| 글로벌 RegTech | 해외 컴플라이언스 플랫폼 | **한국 부동산·가계대출 규제 특유의 경과규정·지역상태 시점 관리**에 특화 |

> `[검증필요]` 경쟁사 실명·가격·기능 비교표는 멘토링 이후 데스크리서치로 채운다. 현재는 카테고리 수준 비교만 신뢰할 수 있다.

### (4) 시장 진입 타이밍 (Why now)

1. **금융권 LLM 도입은 이미 시작됐고, 다음 질문은 "그걸 어떻게 믿느냐"로 이동 중이다.** 검증·거버넌스 수요가 도입 수요를 뒤따른다.
2. **AI 규율 체계 정비** — 국내 AI 기본법 시행(2026.1) 및 금융분야 AI 가이드라인 흐름상, 금융회사는 AI 산출물의 설명·검증·기록 의무를 강화해야 한다. `[검증필요: 조문 단위 확인 후 인용]`
3. **가계대출 규제는 계속 바뀐다.** 6·27, 6·30, 10·15 등 대책이 반복 발생하며, 이는 제품의 **재발성 수요(recurring demand)** 를 보장한다.

# 2. 실현가능성 (Solution)

## 2.1 창업아이템의 개발·사업화 전략

### (1) 시스템 아키텍처

```
[Source Snapshot Store]  원문 + URL + 기관 + retrieved_at + source_hash
        ↓
[Policy Version DB]      published_at / effective_from / effective_to / supersedes
        ↓
[Temporal Policy Resolver]  특정 시점 유효 정책 판정 · 지역상태 버전 관리 · 경과규정 연결
        ↓
[RegChange Extractor]    Before/After 변경 추출 — 모든 주장에 원문 인용 강제
        ↓
[Impact Analyzer]        임팩트 매트릭스(시간축 포함) + 고객·포트폴리오 영향
        ↓
[Rule Change Proposal] + [Test Case Generator]
        ↓
[Human Review / Approval]   DRAFT → REVIEW_REQUIRED → APPROVED / REJECTED
        ↓
[Deterministic Rule Registry / Rule Engine]   ← LLM은 여기에 쓰기 권한이 없다
        ↓
╔══════════════ ASSURANCE LAYER ══════════════╗
║ ① Source Grounding & Citation                ║
║ ② Change & Exception Completeness            ║
║ ③ Temporal / Policy-Version Consistency      ║
║ ④ Rule Regression & Conflict                 ║
║ + Human Escalation 평가 · Audit Trail        ║
╚══════════════════════════════════════════════╝
```

### (2) 설계 원칙 (제품 정체성 — 임의로 뒤집지 않는 결정)

1. **LLM에 실행 권한을 주지 않는다.** LLM은 구조화된 *변경안*만 제안하고, 사람이 승인한 뒤에야 deterministic 룰 레지스트리에 반영된다.
2. **룰엔진의 규칙 로직은 LLM이 생성하지 않는다.** 규칙은 도메인 전문가가 확정하며, 이것이 LLM 출력을 채점하는 **기준점**이 된다. (AI가 AI를 채점하는 순환검증 금지)
3. **영향 탐지는 넓게, 자동판정은 좁게.** 전세대출·신용대출·중도금 등은 "영향 가능성"만 표시(`Potentially impacted — manual review required`)하고 자동판정하지 않는다. 이는 기능 부족이 아니라 **의도된 거버넌스 설계**다.
4. **평가셋을 개발보다 먼저 만들고 DEV / LOCKED TEST / CHALLENGE를 분리한다.** 최종 성능은 개발 중 한 번도 열지 않은 세트에서만 보고한다.
5. **시간축(Phase)을 삭제하지 않는다.** 시행 전 필수 작업과 시행 후 작업(전략 재검토·대외보고 기준 변경·모니터링)은 다른 트리거로 온다.
6. **고객 실데이터·내부문서를 사용하지 않는다.** 공개 원문 + 합성 포트폴리오로 성능을 증명한다. → 도입 시 보안 심사 통과가 쉬워지는 **영업상 이점**이기도 하다.

### (3) 현재까지의 개발 실적 (이미 만들어진 것)

| 컴포넌트 | 상태 | 증거 |
|---|---|---|
| **Deterministic 룰엔진 v1** | ✅ 구현 | `src/regimpact/` — 규칙 명세 §H를 코드화. 지역상태·예외 우선순위(P0~P7)·경과규정(G1~G3). 테스트 23개 |
| **RegChange Extractor + Citation Assurance** | ✅ 구현 | `src/regimpact/extractor/` — structured output. **인용이 원문에 verbatim 존재하는지 deterministic 검증** → 환각 탐지 실측. 테스트 5개 |
| **TC Generator + Rule-Regression** | ✅ 구현 | `src/regimpact/tc_generator/` — **독립 오라클과 차등 검증**(differential testing). 30케이스 6카테고리 Pass Rate 100%. **mutation test로 fixture 방어력 증명**. 테스트 11개 |
| **원문 스냅샷 파이프라인** | ✅ 구현 | 금융위·국토부 보도참고자료 PDF, 관계기관 FAQ HWP 3건 + sha256 + 추출 텍스트 (`docs/sources/`) |
| **규칙 명세서** | ✅ v1 확정 | `docs/05_RULE_SPEC.md` — 사람이 확정한 도메인 명세 |
| **평가지표 정의서** | 🟡 초안 | `docs/metrics_spec.md` — 지표별 분모/분자/임계 정의 |
| **골드 평가셋** | 🟡 설계 확정 | 총 ~115문항 (DEV 40 / LOCKED 40 / CHALLENGE 35). CHALLENGE에 예외·경과규정·시행일·충돌 가중 |
| UI | 🟡 목업 | Stitch 목업 5화면. 실제 구현은 경량 UI로 |

**정량:** Python 코드 약 1,900 라인, **테스트 39개 전량 통과**, 회귀 30케이스 Pass Rate 100%.

> 이 실적의 의미: 사업계획서에서 흔한 "이런 걸 만들겠습니다"가 아니라, **가장 어려운 검증 부분이 이미 돌아간다.** 남은 것은 시장 검증과 제품화다.

### (4) 기술적 차별점 — 왜 따라하기 어려운가

| 차별점 | 내용 | 모방 난이도 |
|---|---|---|
| **차등 검증(differential testing) 오라클** | 룰엔진 출력을 자기 자신으로 채점하지 않고, 명세에서 **독립 유도한 챌린저 구현**과 대조. 회귀가 tautology가 되지 않음 | 높음 — 모델검증 방법론 지식 필요 |
| **경과규정·시점 판정** | 신청 제출 / 전산 접수 완료 / 계약 체결 / 계약금 납부를 **별개 이벤트**로 분리해 판정. 단일 `application_date`로는 못 푸는 문제 | 높음 — 실무 경험 없이는 스키마 자체를 못 만듦 |
| **지역상태의 시점 버전 관리** | 지역명을 문자열로 저장하지 않고 `region_status × effective_from/to`로 관리 | 중 |
| **인용 grounding 검증** | LLM 인용이 원문에 실제 존재하는지 deterministic 대조 → LLM이 LLM을 채점하지 않음 | 중 |
| **실패모드 중심 평가셋** | EXCEPTION·GRANDFATHERING·EFFECTIVE_DATE·CONFLICT 가중 골드셋 | 높음 — 도메인 실패 경험의 산물 |

**해자(moat)의 정체:** 모델이 아니라 **검증 자산**(규칙 명세 + 골드 평가셋 + 회귀 fixture + 실패모드 taxonomy)이다. 모델은 교체 가능하지만 이 자산은 도메인 경험 없이는 축적되지 않는다.

## 2.2 시장진입 및 성과 창출 전략

### (1) 진입 시나리오 — "라이브 파이어(Live Fire)"를 영업 자산으로

가장 강력한 세일즈 증거는 데모가 아니라 **실적**이다.

> 다음 실제 부동산·가계대출 대책이 발표되면, 발표 당일 원문 스냅샷 → 분석 → Rule 변경안 → 테스트케이스 → Assurance 리포트를 **공개적으로 타임스탬프와 함께 기록**한다.
>
> ```
> Live Fire #1 — YYYY-MM-DD Policy Update
> - 공식 발표: HH:MM      - 분석 산출: HH:MM
> - Commit: <hash>        - Source hash: <hash>
> - 결과물: <link>
> ```
>
> 메시지: **"이 도구는 실제 신규 규제를 발표 당일 처리했다."**

### (2) 단계별 진입 경로

| 단계 | 목표 | 핵심 활동 |
|---|---|---|
| **S0. 문제 검증** (1~2개월) | 가정 파괴 | 현직 실무자 5~10명 인터뷰. 공수·재작업 빈도·지불의사 확보 |
| **S1. 무료 파일럿** (2~4개월) | 레퍼런스 1개사 | 저축은행·상호금융 등 **전담 인력이 더 부족한 곳**부터. 실데이터 없이 공개 원문+모의 내규로 PoC |
| **S2. 유료 PoC** (4~8개월) | 매출 발생 + 사례 | 기관 1~2개사 유상 PoC. 산출물: 규제 1건 E2E 리포트 |
| **S3. 제품화** (8~18개월) | 구독 전환 | 온프레미스/VPC 배포 옵션, 감사증적, 다기관 확산 |

### (3) 왜 저축은행·상호금융부터인가 `[가정]`

- 대형은행: 예산은 크지만 도입 절차가 길고 자체 개발 여력이 있음 → 사이클 12개월+
- 저축은행·상호금융: **규제 대응 전담 인력이 절대적으로 부족** → 통증이 더 크고 의사결정이 빠름
- 초기 레퍼런스 확보 후 대형사 진입이 정석 `[검증필요: 실제 도입 사이클을 인터뷰로 확인]`

### (4) 데이터·보안 전략 (도입 장벽 해소)

- 학습·분석에 **고객 개인신용정보를 사용하지 않는다.** 입력은 공개 원문 + 고객사가 제공하는 내규 텍스트.
- 배포 옵션: **온프레미스 / 고객사 VPC / 망분리 환경** 지원을 로드맵에 포함.
- 모델 호출은 교체 가능(ADJUSTABLE). 고객사 정책에 따라 사내 모델·국내 리전 모델로 대체 가능한 구조.
- 모든 판정에 audit trail(원문 해시·모델·프롬프트 버전·룰 버전·승인자) 기록 → **감사 대응 자체가 제품 기능**.

### 창업자-문제 적합성 (Founder–Problem Fit)

이 아이템의 가장 강한 자산은 기술이 아니라 **"이 문제로 야근한 사람이 만들었다"** 는 사실이다.

- 경과규정을 왜 4개의 날짜 이벤트로 쪼개야 하는지 아는 것
- "에러 나는 테스트건"이 무엇인지 아는 것
- 예외·시행일 누락이 원칙 오류보다 위험하다는 것

이는 문헌 조사로 얻을 수 없는 설계 지식이며, 실제로 제품의 스키마와 평가셋 가중치에 그대로 반영되어 있다.
