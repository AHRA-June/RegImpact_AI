## 2026-08-18 — D-02 해결: 문서별 추출 + 문서 간 병합 채택

- **결정:** RegChange 추출을 **문서마다 따로 수행한 뒤 합친다**(Q9 선택지 ①).
  Change Completeness 79%→100%, Exception Recall 50%→100%. 호출 3배(지출은 여전히 0원).
- **전제:** 골드가 required 4 / exception 2로 너무 얇아 튜닝 근거가 되지 못했다 →
  6·30 코퍼스에서 검증 가능한 19+4로 확장(v2). **확장하자마자 단일 패스의 실제 성적이
  79%/50%로 드러났다** — 지표가 좋았던 게 아니라 골드가 물었던 것이 적었다.
- **원인:** 3개 문서를 한 번에 태우면 한 문서의 축약 서술("생애최초, 정책모기지 **등**")이
  다른 문서의 완전한 열거를 가린다. 프롬프트 지시로는 두 모델 모두 같은 실패를 반복했다.
- **부수:** 문서별 결과를 원문 해시 키로 캐시한다 — 무과금 경로에서 한 실행이 8분이라
  후속 단계 실패로 완료된 LLM 작업을 잃는 비용이 크다.

## 2026-08-18 — 유사도 기반 병합 기각 (지표가 통과했는데도)

- **기각:** 요약문 유사도로 중복을 합치는 방식. 골드 대비 점수는 임계값 0.3까지 100%/100%였다.
- **이유:** 실제로 무엇이 합쳐지는지 열어 보니 임계값 0.6에서도 "생애최초 60% 유지"와
  "서민·실수요자 60% 유지", "서민 요건 9천만원/8억"과 "생애최초 요건 7천만원/6억",
  "일반 주담대 경과규정"과 "사업자 주담대 경과규정"이 합쳐지고 있었다. 개체만 다르고 문장
  구조가 같아 텍스트 유사도로는 구분되지 않는다 — **임계값 문제가 아니다.**
- **골드가 통과시킨 이유:** 골드의 사실이 넓어 다른 항목이 대신 맞혀 주었다. 즉 **골드가
  과병합을 탐지할 만큼 예민하지 않았다.** 지표만 보고 채택했다면 D-02를 병합 단계에서 되살릴 뻔했다.
- **채택한 규칙:** 같은 문서 안의 항목은 건드리지 않는다(모델이 나눴다면 나눈 이유가 있다).
  합치는 것은 서로 다른 문서가 같은 사실을 말한 경우뿐이며 ①다른 문서 ②내용 지문(카테고리·수치·
  개체어) 일치 ③유사도 ≥ 0.5를 모두 만족해야 한다. 합쳐진 항목은 다른 문서 인용을
  `corroborations`로 보존한다 — 여러 공문이 같은 변경을 말했다는 사실이 근거의 강도다.
- **교훈:** 지표 통과는 채택 근거로 충분하지 않다. **무엇이 바뀌는지 직접 열어 봐야 한다.**

## 2026-08-18 — 자동화율 분모에서 Discovery 행 제외

- **결정:** `ImpactMatrix.automation_rate`의 분모를 **코어 행**으로 고정한다.
- **이유:** 추출 재현율을 100%로 올리자 Discovery 행이 4→18로 늘면서 자동화율이 50%→27%로
  '하락'했다. Discovery는 정의상 자동판정하지 않는 항목이므로, **탐지를 잘할수록 지표가 나빠지는
  구조**였다. 코어 작업의 자동화는 전혀 나빠지지 않았다(코어 기준 67%).
- 앞선 "자동판정 불가 22.4%"(심사 판정 vs 영향 측정)와 같은 종류의 분모 문제다.

## 2026-08-18 — D-03 철회: "haiku 인용 환각 25%"는 측정 오차였다

- **철회:** 2026-08-18 1차에 보고한 "haiku-4-5 Unsupported Claim Rate 25% — 모델 선택이 곧
  리스크 프로파일 선택"은 **틀렸다.** 저장된 실행을 원문과 직접 대조하니 12건 전부 원문에 있었고,
  실제 Unsupported Claim Rate는 **0%** 다.
- **원인:** 인용 대조가 공백을 "단일 공백으로 축약"만 했는데, PDF/HWP 추출본은 **단어 중간에서도
  줄을 바꾼다**("규제\n지역 내"). 모델이 자연스러운 "규제지역 내"로 옮겨 적으면 불일치가 됐다.
  모델이 인용을 지어낸 것이 아니라 **채점기가 원문 추출 아티팩트를 환각으로 오인**했다.
- **조치:** `evaluate.py::_norm`을 공백 전부 제거로 변경. 다른 단어를 지어낸 인용은 여전히 잡히며,
  회귀 테스트 2건으로 양방향 고정.
- **결정 갱신:** 코어 모델 sonnet-5는 **유지**하되 근거를 교체한다 — 인용 환각이 아니라
  추출 완전성(19건 vs 12건).
- **교훈(기록해 둘 것):** 지표가 나쁘게 나왔을 때 모델을 의심하기 전에 **측정기를 먼저 의심한다.**
  같은 오차가 골드셋 QA 첫 채점에서도 반복됐다(실패 12건 전부 표현 차이).

## 2026-08-18 — 골드셋 QA 평가 하네스: LLM 심판을 쓰지 않는다

- **결정:** 채점은 `gold_facts` 부분문자열 매칭 + 인용의 원문 verbatim 대조로만 한다.
  둘 다 결정적이며 LLM 심판을 쓰지 않는다.
- **이유:** LLM이 LLM을 채점하면 그 채점의 신뢰도를 다시 검증해야 하고, 그 회귀는 끝나지 않는다.
  대가는 표현이 달라 놓치는 false negative이며, 그래서 `gold_facts`를 짧은 원자 문자열로 둔다.
- **채점기 관대화의 경계:** 표면 정규화(공백·날짜 표기·따옴표)와 `|` 동의 표현만 허용한다.
  동의어 자동 추론은 하지 않는다. `|` 대안은 **모델이 실제로 같은 내용을 말한 경우에만** 추가하고
  골드 파일에 남겨 감사 가능하게 한다. `tests/test_qa_eval.py`가 양방향으로 고정한다 —
  표면 차이는 통과, 내용 차이는 실패.
- **부수 수정:** provider 레이어(`backends.py`)가 RegChange 스키마에 붙어 있어 QA 응답을 만들 수
  없었다. 검증기·지시문을 주입 가능하게 바꿨다 — provider를 추상화하는 레이어가 특정 출력 형식을
  강제하고 있던 설계 결함이다.

## LOCKED 원칙 (브리프 §0 — 정체성, 임의 변경 금지)

아래는 확정된 정체성 결정이다. 변경하려면 먼저 사용자에게 이유를 설명하고 승인받은 뒤 이 로그에 기록한다.

1. E가 제품이고 A가 신뢰의 기반이다. (E=규제 변경 영향분석, A=Assurance)
2. 챗봇이 아니라 검증 가능한 의사결정 지원 시스템을 만든다.
3. 주택구입목적 주담대 규제의 수직 슬라이스를 유지한다.
4. 실행 가능한 룰엔진의 규칙 로직은 LLM이 생성하지 않는다.
5. 평가셋을 개발보다 먼저 만들고, DEV / LOCKED TEST / CHALLENGE를 분리한다.
6. Assurance Layer와 Test Case Generator는 일정이 밀려도 자르지 않는다.
7. 임팩트 매트릭스의 시간축(Phase)은 삭제하지 않는다.
8. 실제 회사 내부문서·고객데이터를 사용하지 않는다.
9. LLM은 금융 의사결정을 직접 실행하지 않고 변경안·영향분석·검토자료를 제안한다.
10. 자동화 범위보다 검증 가능성과 추적 가능성을 우선한다.

### 2026-08-10 · 골드 평가셋 규모 100~120으로 축소 (Q1) · ✅ 승인됨
- **결정:** 골드셋 총 규모를 원안 150~200에서 **100~120**으로 축소. CHALLENGE 비중을 상대적으로 강화.
- **확정 split (권장 수치, 총 ~115):**
  | Split | 규모 | 용도 |
  |---|---:|---|
  | DEV | 40 | 프롬프트·retrieval·extractor 튜닝 |
  | LOCKED TEST | 40 | 최종 성능평가 (개발 중 튜닝 금지) |
  | CHALLENGE | 35 | 예외·경계·충돌·모호 중심 적대적 평가 |
- **CHALLENGE 카테고리 가중:** EXCEPTION / GRANDFATHERING / EFFECTIVE_DATE / CONFLICT 비중을 높게(브리프 §11 철학). 세부 건수는 도메인 검수 시 확정.
- **이전값:** 150~200 (브리프 §11, §12).
- **이유:** 1인이 전체 메타데이터 완비+도메인 검수+3-way split을 손수 만들면 그 자체가 2~3주. 빌드 시간과 충돌. 포트폴리오는 양보다 질 — 잘 만든 CONFLICT 10개 > NORMAL 40개. CHALLENGE가 프로젝트의 진짜 차별점.
- **LOCKED 정합성:** ADJUSTABLE. 브리프 §0은 "평가셋 세부 건수(총 150~200 범위)"를 ADJUSTABLE로 명시. 축소는 LOCKED §0-5(평가셋 우선·3-way 분리)를 훼손하지 않음 — split 구조는 유지.
- **성공 기준 변경:** "150 못 채우면 실패"가 아니라 **"실패모드 카테고리 커버리지가 채워지면 충분"**.
- **관련 파일:** `docs/metrics_spec.md`(평가셋 규모·split 섹션), `docs/03_OPEN_QUESTIONS.md` Q1 해결.

### 2026-08-10 · Assurance 체크 "구현 깊이" 차등 (수를 줄임) · ✅ 승인됨
- **결정:** Assurance Layer의 11개 체크를 전부 동일 깊이로 구현하지 않는다.
  **정량 측정하는 4개 dimension**만 깊게 가고, 나머지는 "정의+루브릭+소규모 예시(로드맵)"로 둔다.
  - **① 깊게 정량 측정 (4):**
    1. Source Grounding & Citation → Citation Correctness, Unsupported Claim Rate, Source Contradiction Rate
    2. Change & Exception Completeness → Change Completeness, Exception Recall, Grandfathering Recall
    3. Temporal / Policy-Version Consistency → Policy-version Consistency, Effective-date Accuracy
    4. Rule Regression & Conflict → Rule-regression Pass Rate, Conflict/Boundary-case Pass Rate
  - **② 유지하되 가볍게 (로드맵):** Human Escalation Evaluation (Escalation Recall/Precision, High-risk Miss Rate)
  - **③ 항상 켜지는 인프라 (metric 아님):** Audit trail, Approval status field
- **이유:** 6주·1인·LLM 첫 실무에 11개를 모두 깊게 구현하면 전부 얕은 스텁이 되어 오히려 핵심(A)이 약해 보임. 폭보다 깊이 우선.
- **LOCKED 정합성:** 브리프 §0-6 "Assurance Layer는 자르지 않는다"와 충돌하지 않음.
  **레이어(컴포넌트)와 아키텍처상 위치는 그대로 유지**하고, 개별 체크의 *구현 깊이*만 차등한다. 레이어를 제거·삭제하는 것이 아님. → LOCKED 변경 아님.
- **미확정 여백:** "깊게 갈 4개"의 구체 조합은 사용자가 escalation을 4번 대신 승격하고 싶으면 조정 가능. (현재는 위 4개로 확정)
- **관련 파일:** `docs/metrics_spec.md`(깊이 태그 반영), `docs/03_OPEN_QUESTIONS.md` Q2 해결.
