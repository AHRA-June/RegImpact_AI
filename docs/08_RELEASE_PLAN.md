## 1. 배포 정의 — 무엇을 올리나

리크루터·면접관이 **링크 하나**로 들어와서 이 순서로 읽는 것을 목표로 한다.

```
랜딩 (index.html)
├─ 이 시스템이 푸는 문제 · 30초 요약
├─ 📊 화면 5개        ← 이미 있음. 엔진 실제 출력
│    규제분석 · 임팩트매트릭스 · 룰 · Assurance · 포트폴리오
├─ 📄 검증보고서       ← md → html 렌더 필요
├─ 📄 Model/System Card · AI Risk Register   ← md → html 렌더 필요
└─ 🧪 인터랙티브 플레이그라운드   ← Day 2 (JS 포팅 + 대조 하네스)
```

## 2. 일자별 계획

### Day 1 — 링크부터 띄운다 (오늘)

| # | 작업 | 백로그 | 규모 |
|---|---|---|---|
| 1 | md → HTML 렌더러 (`docrender`) — 검증보고서·카드·레지스터를 읽을 수 있게 | S-18 | 중 |
| 2 | 랜딩 허브 `index.html` — 5화면 + 문서 3종 진입점, 빌드 커밋 표시 | S-18 | 중 |
| 3 | `vercel.json` · `.vercelignore` · 빌드 스크립트 (`tools/build_site.py`) | S-17 | 소 |
| 4 | **1차 배포 → URL 확보** | S-17 | 소 |

> **URL 을 먼저 확보하는 것이 이 계획의 핵심이다.** 완성도를 올린 뒤 배포하면
> 3일차에 배포 문제가 터졌을 때 되돌릴 시간이 없다. 1일차에 띄워 놓고 2·3일차에 개선한다.

**Day 1 종료 조건:** 공개 URL 에서 5화면 + 문서 3종이 읽힌다.

### Day 2 — 만져볼 수 있게

| # | 작업 | 백로그 | 규모 |
|---|---|---|---|
| 5 | `tools/export_fixtures.py` — Python 엔진 판정을 픽스처로 export | S-17 | 중 |
| 6 | 룰엔진 JS 포팅 + `verify_js_port.mjs` 전 케이스 대조 | S-16+17 | **대** |
| 7 | 인터랙티브 플레이그라운드 화면 (차주 조건 바꾸면 즉시 판정) | S-16 | 중 |
| 8 | 2차 배포 | — | 소 |

> ⚠️ **6번이 이번 3일의 최대 리스크다.** 플레이그라운드에는 룰엔진 JS 재구현이 들어가는데,
> 그냥 옮기면 PR #4에서 제거한 하드코딩이 되살아나고 아무도 테스트하지 않는 두 번째 룰
> 구현이 생긴다. 그래서 **Python 엔진 판정을 픽스처로 뽑아 JS 포팅본을 전 케이스 대조**하는
> 하네스가 먼저다(5번). 5번 없이 7번만 하면 안 된다.
>
> 시간이 부족하면 **7번을 버리고 5·6번만** 한다 — 대조 하네스 자체가 포트폴리오 가치가 있다.

**Day 2 종료 조건:** 플레이그라운드가 뜨고, JS 포팅본이 Python 엔진과 전 케이스 일치한다.
